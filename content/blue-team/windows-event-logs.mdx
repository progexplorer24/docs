# Windows Event Log

This document provides foundational and practical knowledge for analyzing Windows Event Logs from a cybersecurity perspective. The focus is on understanding the log structure, key event IDs, and leveraging powerful query techniques.

---

## 1. Windows Event Log Fundamentals

Windows Event Logs are the primary record-keeping mechanism of the operating system. For a SOC analyst, they are a critical source of truth for investigating security incidents, troubleshooting issues, and hunting for threats.

### Log Categories

Windows organizes logs into several default categories. The most important ones for security analysis are:

* **Security**: The most critical log for a SOC analyst. It contains events related to security, such as logon attempts (successful and failed), privilege changes, and object access. This log is configured via Audit Policies.
* **Application**: Contains logs from applications running on the system. Application errors seen here can sometimes indicate security issues, such as a buffer overflow attempt causing a crash.
* **System**: Contains events logged by Windows system components, such as driver failures or services starting and stopping. A service failing to start or an unexpected reboot could be signs of malicious activity.
* **Setup**: Contains events related to the installation and setup of Windows and its components.
* **Forwarded Events**: A centralized log that contains events collected from other computers on the network.

### The Anatomy of an Event

Each log entry is an "Event" with a standardized structure. Understanding these components is key to interpreting the data.

| Component | Description |
| :--- | :--- |
| **Log Name** | The category the event belongs to (e.g., `Security`). |
| **Source** | The software or component that generated the event (e.g., `Microsoft-Windows-Security-Auditing`). |
| **Event ID** | A unique number identifying the specific event type. **This is the most important field for filtering.** |
| **Level** | The severity of the event (e.g., `Information`, `Warning`, `Error`). In the Security log, this is usually `Audit Success` or `Audit Failure`. |
| **User** | The user account that triggered the event. Can be `SYSTEM` for system-level actions. |
| **Logged** | The timestamp when the event was recorded. |
| **Computer** | The name of the computer where the event occurred. |
| **XML Data** | The full event details in XML format. This contains rich, specific data not visible in the summary view, such as source IP addresses or specific privileges. |

## 2. Practical Analysis with Event Viewer

While GUIs are useful, the real power for a SOC analyst comes from building precise filters.

### Writing Custom XML Queries (XPath)

The most powerful way to filter logs in Event Viewer is by writing custom XML queries. This allows you to pinpoint events with extreme precision, something that is impossible with the standard UI filters.

You can access it via **Filter Current Log...** -> **XML** tab -> **Edit query manually**.

The basic structure looks like this:

```xml
    <QueryList>
      <Query Id="0" Path="Security">
        <Select Path="Security">
            *[System[EventID=4624]]
            and
            *[EventData[Data[@Name='TargetUserName']='JohnDoe']]
        </Select>
      </Query>
    </QueryList>
```

**Key parts to understand:**
* `<Select Path="Security">`: Specifies which log you are querying (e.g., `Security`, `System`, `Application`).
* `*[System[...]]`: This part filters on the general event properties, like `EventID`.
* `*[EventData[...]]`: This part filters on the specific, detailed data inside the event's XML view. `Data[@Name='FieldName']` is how you target a specific piece of data.

#### Practical Query Examples

| Goal | XML Query Snippet (Place inside `<Select>...</Select>`) |
| :--- | :--- |
| **Find all failed logons (4625) for a specific user.** | `*[System[EventID=4625]] and *[EventData[Data[@Name='TargetUserName']='someuser']]` |
| **Find successful RDP logons (Type 10).** | `*[System[EventID=4624]] and *[EventData[Data[@Name='LogonType']='10']]` |
| **Find events related to a specific logon session.** | `*[EventData[Data[@Name='SubjectLogonId']='0x3e7']]` |
| **Find when a specific service was installed.** | `*[System[EventID=7045]] and *[EventData[Data[@Name='ServiceName']='EvilSvc']]` |
| **Find when a specific scheduled task was created.** | `*[System[EventID=4698]] and *[EventData[Data[@Name='TaskName']='\SomeMaliciousTask']]`|

## 3. Key Concepts for Deeper Investigation

Some events contain complex data that requires deeper knowledge to interpret.

### SACL, ACL, and SDDL

These concepts relate to object permissions and auditing.

* **ACL (Access Control List)**: A list of permissions attached to an object (like a file or registry key). It answers the question: "**Who can do what?**"
* **SACL (System Access Control List)**: A special list that controls **auditing**. It answers the question: "**Whose actions should be logged?**" If an action matches an entry in the SACL, a security event is generated.
* **SDDL (Security Descriptor Definition Language)**: A text format used to represent all these permissions (ACLs and SACLs). When you see `NewSd` or `OldSd` in an event, it's showing you the permissions in SDDL format.

### Special Privileges (Tokens)

When a user logs on, their session is granted a set of "privileges" in an access token. Most are standard, but some are highly sensitive and should be monitored closely.

* **Event ID 4672 (Special privileges assigned to new logon)** alerts you when an account logs on with these high-level rights.
* **`SeDebugPrivilege`** is one of the most critical. It allows a user to inspect and modify the memory of other processes, a common technique used by malware (e.g., Mimikatz) to steal credentials. An unexpected process running with this privilege is a major red flag.

## 4. Important Windows Event IDs

This is a reference list of event IDs that are particularly useful for security monitoring.

### Security Logs

| Event ID | Event Name | Why It's Important for a SOC Analyst |
| :--- | :--- | :--- |
| **1102** | The audit log was cleared | **Red Flag.** Common attacker technique to cover tracks. Should always be investigated. |
| **4624** | An account was successfully logged on | Baseline for normal user activity. Look for anomalies (off-hours, unusual hosts). |
| **4625** | An account failed to log on | High numbers can indicate a brute-force attack. |
| **4648** | Logon with explicit credentials | Key indicator of **lateral movement** (e.g., `runas` command). |
| **4672** | Special privileges assigned to new logon | Alerts that a highly privileged session has started. Monitor for abuse. |
| **4698** | A scheduled task was created | Common **persistence mechanism** for attackers. |
| **4719** | System audit policy was changed | Attacker may be trying to disable logging to avoid detection. |
| **4738** | A user account was changed | Monitor for unauthorized privilege escalation or changes. |
| **4776** | Domain controller credential validation | Tracks authentication attempts against the DC. Failures can indicate brute-forcing. |
| **5140** | A network share object was accessed | Monitor for unauthorized access to sensitive file shares. |
| **7045** | A new service was installed | Attackers often install malware as a service for persistence. |

### System Logs

| Event ID | Event Name | Why It's Important for a SOC Analyst |
| :--- | :--- | :--- |
| **6005** | Event Log service started | Marks a system boot. Correlate with other events to investigate reboots. |
| **6006** | Event Log service stopped | Marks a system shutdown. Unexpected shutdowns can indicate a crash or malicious action. |
| **7040** | Service startup type changed | An attacker might change a service from "Disabled" to "Automatic" for persistence. |

## 5. Sysmon: Advanced Threat Detection

While standard Windows logs are useful, **System Monitor (Sysmon)** provides much deeper visibility into system activity. It's a Windows system service and driver that logs advanced process, network, and file activity to its own event channel. For a SOC analyst, Sysmon is an indispensable tool for threat hunting.

### Installation & Configuration

Sysmon is not installed by default. You must install it manually from an administrator command prompt.

* **Installation Command**: This command installs the service with a good baseline for hashing and logging.
    `sysmon.exe -i -accepteula -h md5,sha256,imphash -l -n`
* **Applying a Configuration**: Sysmon's true power comes from using a detailed XML configuration file to filter out noise and focus on suspicious events.
    `sysmon.exe -c your_config_file.xml`
* **Recommended Configurations**:
    * **SwiftOnSecurity/sysmon-config**: A comprehensive, well-regarded configuration that is excellent for general-purpose use.
    * **olafhartong/sysmon-modular**: A modular approach that allows you to piece together a configuration that fits your specific needs.

### Key Sysmon Event IDs for Threat Hunting

Sysmon generates many types of events. These are some of the most critical for security analysis.


| Event ID | Event Name | Use Case for a SOC Analyst 🕵️ |
| :--- | :--- | :--- |
| **1** | Process Creation | The most fundamental event. Provides command-line details for every process started. |
| **3** | Network Connection | Tracks every outbound network connection, showing which process initiated it. |
| **7** | Image Load | Tracks when a process loads a DLL. Crucial for detecting DLL hijacking and code injection. |
| **8** | Create Remote Thread | Detects when one process injects a thread into another. A core technique for malware. |
| **9** | Raw Access Read | Detects reading from a drive's raw sectors, often used to bypass file access controls. |
| **10** | Process Access | Tracks when one process accesses another. Key for detecting credential dumping against `lsass.exe`. |
| **11** | File Create | Can be used to track when malware drops files to disk in sensitive locations. |
| **12, 13, 14**| Registry Events | Monitors for changes to registry keys and values, especially persistence locations. |
| **15** | File Create Stream Hash | Logs the creation of Alternate Data Streams (ADS), often used by browsers to mark downloaded files. |
| **17, 18** | Pipe Events | Logs named pipe creation and connection, used by malware for inter-process communication. |
| **19, 20, 21**| WMI Events | Tracks the creation of WMI filters and consumers, a common persistence technique. |
| **22** | DNS Query | Logs all DNS queries made by a process. Excellent for identifying connections to malicious domains. |

### Detection Recipes & IOCs

Here are practical recipes for detecting common attack techniques using Sysmon data.

#### Recipe 1: Detecting DLL Hijacking

* **Threat**: An attacker tricks a legitimate application into loading a malicious DLL by placing it in the same directory as a copy of the application.
* **Key Sysmon Event**: `Event ID 7 (ImageLoad)`
* **Common Indicators of Compromise (IOCs)**:
    * A legitimate Windows process (e.g., `calc.exe`) has an `Image` path in an unusual location, like a user's `Desktop` or `Downloads` folder.
    * A well-known system DLL (e.g., `WININET.dll`) is loaded from that same unusual path, instead of from `C:\Windows\System32\`.
    * The `Signature` of the loaded DLL is `Unsigned`, when the legitimate version is signed by Microsoft.

#### Recipe 2: Detecting Unmanaged Code Injection

* **Threat**: An attacker injects .NET or PowerShell code into a process that does not normally run it. This is a common fileless attack technique.
* **Key Sysmon Event**: `Event ID 7 (ImageLoad)`
* **Common Indicators of Compromise (IOCs)**:
    * An `Image` that is normally unmanaged (e.g., `spoolsv.exe`, `explorer.exe`, `notepad.exe`) loads .NET runtime modules.
    * Look for an `ImageLoaded` path containing **`clr.dll`** or **`clrjit.dll`** in these unexpected processes.

#### Recipe 3: Detecting Credential Dumping (LSASS Access)

* **Threat**: An attacker uses a tool like Mimikatz to access the memory of the **Local Security Authority Subsystem Service (LSASS)** to steal passwords and hashes.
* **Key Sysmon Event**: `Event ID 10 (ProcessAccess)`
* **Common Indicators of Compromise (IOCs)**:
    * The `TargetImage` is `C:\Windows\System32\lsass.exe`.
    * The `SourceImage` (the process accessing LSASS) is an unknown executable, `powershell.exe`, or any process running from a temporary or user-writable location.
    * The `GrantedAccess` code indicates a request for powerful permissions needed to read memory. Look for codes like `0x1010` or `0x1410`.

## 6. Event Tracing for Windows (ETW): Deeper Telemetry

While Sysmon is powerful, it is built on top of a more fundamental Windows technology: **Event Tracing for Windows (ETW)**. ETW is a high-speed, kernel-level tracing facility that provides incredibly detailed information about system and application activity, far beyond what standard event logs capture.

### Core ETW Concepts

ETW operates on a publish-subscribe model. Understanding its components helps you know what's possible to monitor.

* **Providers**: These are the source of the data. OS components (like the kernel), applications, and drivers (like Sysmon) register as providers to generate specific events. Windows has over 1,000 built-in providers.
* **Controllers**: These start and stop event tracing sessions, telling providers to start or stop sending events. The built-in `logman.exe` is a primary example.
* **Consumers**: These subscribe to one or more sessions to process the events. A consumer could be a security tool (like an EDR agent) or a process that writes events to an `.etl` log file for offline analysis.

### Practical Interaction with `logman.exe`

The `logman.exe` command-line utility is the primary built-in tool for interacting with ETW sessions.

1.  **List Active Sessions**: To see what is currently being traced on a system, use the `query -ets` command. This can reveal monitoring tools (like Sysmon) or potentially suspicious custom tracing sessions.
    `logman.exe query -ets`

2.  **Inspect a Specific Session**: To see which providers are feeding into a specific session, query it by name. This shows you exactly what data is being collected.
    `logman.exe query "EventLog-System" -ets`

3.  **Discover Available Providers**: To see all providers registered on the system, use the `query providers` command. Since the list is huge, it's best to pipe it to `findstr` to search for something specific.
    `logman.exe query providers | findstr /i "PowerShell"`

### Key ETW Providers for Security

While there are thousands of providers, some are exceptionally valuable for security monitoring.

| Provider Name | Why It's Important for a SOC Analyst 🕵️ |
| :--- | :--- |
| **Microsoft-Windows-Kernel-Process** | Provides granular detail on process and thread creation/termination. |
| **Microsoft-Windows-Kernel-Network** | Offers visibility into network activity at the kernel level, including TCP/IP events. |
| **Microsoft-Windows-Kernel-Registry** | Monitors registry operations, useful for detecting persistence and configuration changes. |
| **Microsoft-Windows-PowerShell** | The primary source for detailed PowerShell script block logging and module loading. |
| **Microsoft-Windows-DNS-Client** | Gives visibility into DNS client activity, crucial for detecting C2 communication and DNS tunneling. |
| **Microsoft-Windows-Threat-Intelligence** | **(Restricted)** A high-value provider that logs extremely suspicious activity like `WriteProcessMemory` calls, but requires special permissions (Protected Process Light - PPL) to be consumed. EDRs and AV products often use this. |
| **Microsoft-Windows-Security-Mitigations** | Tracks the operations of security mitigations (like EMET or Windows Defender Exploit Guard), which can identify bypass attempts. |
| **OpenSSH** | If used, this provider offers insights into SSH connection attempts and authentication. |

## PowerShell for Log Analysis

While the Event Viewer GUI is useful for quick checks, analyzing logs in bulk for threat hunting or incident response requires a more powerful and scriptable approach. **PowerShell**, and specifically the `Get-WinEvent` cmdlet, is the industry-standard tool for this.

### Discovering Logs and Providers

Before you can query logs, you need to know what's available.

* **List All Available Logs**: Use the `-ListLog *` parameter to get a complete list of log channels on the system.

    ```powershell
    Get-WinEvent -ListLog * | Select-Object LogName, RecordCount, IsEnabled | Format-Table -AutoSize
    ```

* **List All Event Providers**: Use the `-ListProvider *` parameter to see all sources that can generate events.

    ```powershell
    Get-WinEvent -ListProvider * | Select-Object Name, LogLinks | Format-Table -AutoSize
    ```

### Basic Event Retrieval

You can pull events from either live system logs or offline `.evtx` files.

* **From a Live Log**: Use the `-LogName` parameter. The `-MaxEvents` parameter is useful to limit output.

    ```powershell
    # Get the 10 most recent Security log events
    Get-WinEvent -LogName 'Security' -MaxEvents 10
    ```

* **From an Offline `.evtx` File**: Use the `-Path` parameter. This is essential for forensics and analyzing logs from other machines.

    ```powershell
    # Get the 10 most recent events from an exported Sysmon log file
    Get-WinEvent -Path 'C:\IR\logs\sysmon.evtx' -MaxEvents 10
    ```

* **Getting the Oldest Events**: To view events chronologically, add the `-Oldest` switch.

    ```powershell
    # Get the first 10 events from the System log
    Get-WinEvent -LogName 'System' -Oldest -MaxEvents 10
    ```

### High-Performance Filtering (Server-Side)

Filtering events *before* they are returned to PowerShell is vastly more efficient than pulling everything and filtering it later. **Always use one of these methods when possible.**

#### Using `-FilterHashtable` (Recommended Method)

This is the easiest, most readable, and highly efficient way to filter events. You create a PowerShell hash table (a key-value dictionary) to define your filter criteria.

**Common Keys for `-FilterHashtable`:**

| Key | Description | Example Value |
| :--- | :--- | :--- |
| `LogName` | The name of the event log channel. | `'Security'` or `'Microsoft-Windows-Sysmon/Operational'` |
| `ProviderName`| The name of the event provider. | `'Microsoft-Windows-Sysmon'` |
| `ID` | The Event ID. Can be a single ID or an array. | `4625` or `@(1, 3, 10)` |
| `StartTime` | The start of a date range. | `(Get-Date).AddDays(-7)` |
| `EndTime` | The end of a date range. | `(Get-Date)` |
| `Path` | The path to an `.evtx` file for offline analysis. | `'C:\IR\logs\sysmon.evtx'` |

**Example 1: Find Sysmon Process Create and Network Connection events.**

```powershell
$filter = @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    ID = 1, 3
}
Get-WinEvent -FilterHashtable $filter | Select-Object TimeCreated, ID, Message
```

**Example 2: Find failed logons in the last 24 hours.**

```powershell
$filter = @{
    LogName = 'Security'
    ID = 4625
    StartTime = (Get-Date).AddDays(-1)
}
Get-WinEvent -FilterHashtable $filter | Select-Object TimeCreated, Message
```

**Using `-FilterXml` and `-FilterXPath`**

For complex queries that a hash table cannot handle (like complex OR conditions on event data), you can use XML-based filters.

* `-FilterXml`: This method uses the same XML query structure as the Event Viewer GUI.

  **Example: Find Sysmon events for suspicious DLLs being loaded.**

  ```powershell
  $xmlQuery = @"
  <QueryList>
    <Query>
      <Select Path="Microsoft-Windows-Sysmon/Operational">
        *[System[EventID=7]] and 
        (*[EventData[Data='mscoree.dll']] or *[EventData[Data='clr.dll']])
      </Select>
    </Query>
  </QueryList>
  "@
  Get-WinEvent -FilterXml $xmlQuery
  ```

* `-FilterXPath`: This method uses the XPath query language for more concise, powerful filters.

  **Example: Find network connections (Sysmon ID 3) to a specific suspicious IP.**
  ```powershell
  $xPath = "*[System[EventID=3] and EventData[Data[@Name='DestinationIp']='52.113.194.132']]"
  Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -FilterXPath $xPath
  ```
